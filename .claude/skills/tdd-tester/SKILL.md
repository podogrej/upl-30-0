# TDD с разделением ролей

Тестировщик и разработчик всегда разные агенты. Тестировщик не пишет код продукта, разработчик не правит тесты, чтобы они прошли.

## Роль тестировщика

1. Прочитай задачу и критерии приёмки. Выпиши в задаче, на каких границах (публичный интерфейс: функция, эндпоинт, экран) ты проверяешь поведение, и по строке, что каждая ловит и что пропускает. Человека не спрашивай, он увидит это в PR.
2. Пиши по одному тесту на срез: один тест, потом передать разработчику, потом следующий. Не пиши все тесты заранее.
3. Запусти тест и убедись, что он красный по правильной причине (нет поведения, а не опечатка).
4. Передай разработчику: путь к тесту и команда запуска.

## Роль разработчика

Пиши минимум кода, чтобы тест позеленел. Ничего впрок. Тесты не трогай; если тест неверен, верни тестировщику с объяснением.

## Что такое хороший тест

- Проверяет поведение через публичный интерфейс, а не внутренности. Критерий: тест не ломается при рефакторинге, если поведение то же.
- Читается как спецификация: «пользователь может оформить заказ с валидной корзиной».
- Ожидаемое значение берётся из независимого источника: готовый литерал, пример из задачи, спецификация. Нельзя пересчитывать его так же, как код (`expect(add(a,b)).toBe(a+b)`).
- Не мокает внутренние зависимости. Мокать можно только внешние границы: сеть, время, платёжка.

## Приёмка

Перед тем как закрыть срез, PM применяет verification-before-completion: сам запускает тесты и смотрит diff.
