# План: раздел «Твої цифри» на странице игрока

Раздел показывает игроку его стиль и рекорды по всем его сезонам, как «Your numbers» в 38-0. Большую часть блоков можно посчитать уже сейчас из `seasons.xi` (имя, слот, клуб, год, рейтинг `r0`, голы `g`, передачи `a`, форма `f` по каждому из 11 игроков). Не хватает одного: кого игроку предлагали, но он не взял (блок «Відхилені» и «взял из предложенных»). Считать нужно одной RPC на сервере с проверкой секрета устройства, без записи с клиента. В MVP идут 6 блоков, которые работают на старых данных; «Відхилені» и сравнение с лигами — вторая очередь.

Источники: `seasons` (колонки: `player_id, created_at, day, mode, format, club, formation, year, era, w, d, l, pts, place, gf, ga, xi, tbl, perfect, practice, verified`; индекс `seasons_player_idx (player_id, created_at desc)`), `season_seeds` (только seed/хеш состава, без игроков — для блоков не нужна), `trophies`, `daily_results`, `vd_results`. Фильтр как в `player_profile`: `not practice and mode <> 'practice' and verified is not false`.

## 1. Блоки: хватает ли того, что уже хранится

| Блок | Из чего | Можно сейчас? |
|---|---|---|
| Заголовок-вывод о стиле | метрики из `xi` (доля игроков «раз и больше никогда», доля топ-1, число клубов, средний `r0`, доля «андердогов») | Да |
| Твій рекорд | `count`, `w/d/l`, `pts`, `gf/ga`, лучший сезон (уже есть `best` в `player_profile`) | Да |
| Твоя 11-ка | самый частый `id` на каждом `slot` в любимой `formation`; в карточке: раз, разных сезонов, голы `g` за тебя, % побед «с ним / без него» | Да, кроме «взял из предложенных» |
| Самый частый, бомбардир | `id` по числу; сумма `g` по `id`; `g` за сезон; лучший клуб-сезон (`c`,`y`) | Да (есть `fav_player`) |

| Очки по режимам | `pts` по `day/mode/format` (бакеты как в `player_profile`) | Да |
| Відхилені | кого пропускал | Нет, нужен лог предложенного |
| Откуда игроки | доля по `x->>'c'` (есть `fav_club`) | Да |
| «Один сезон і більше ніколи» | `id`, у которых `count = 1` | Да |
| Вехи | первый `w = 30` (`perfect`), первый «вылет» (`place` в зоне вылета; границу сверить с движком), сезон №100 (`row_number`) | Да |
| Клуб 100 | матчей с игроком = 30 × число сезонов с ним (состав играет все 30 туров; сверить по движку) | Да |
| Сравнение с лигами | агрегаты участников `league_members` / `fl_members` | Да, но дорого и с приватностью — вторая очередь |

### Что начать сохранять для «Відхилені»
Сейчас в базе нет ни одной записи о том, что показало колесо. Реконструировать нельзя: список зависит от свободных слотов, уже взятых игроков и рероллов. Предлагаю: в `/api/save` принимать необязательное поле `off` — по каждому из 11 пиков массив `id` показанных игроков (короткие id, без имён). Хранить в новой таблице `season_offers (season_id bigint pk, player_id uuid, off jsonb, created_at)`, а не в `seasons`: у `seasons` публичное чтение для anon, а предложенные игроки публиковать незачем.
- Объём: 11 пиков × ~10–15 id × ~8 байт ≈ 1–1,5 КБ на сезон; 1000 сезонов на игрока ≈ 1,5 МБ. Сравнимо с `xi` (около 1 КБ). Контролировать размер таблицы после выпуска.
- Приватность: таблица без политик для anon, чтение только через RPC владельца (device + secret). Чужим не показывать, в `delete_player` — удалять. Старые сезоны блока не получат (он будет «с такой-то даты»).
- Клиент ничего не пишет в базу напрямую: поле едет в существующем `/api/save` и проверяется там же (длина, формат id).
- Зачёт: `/api/verify` полем `off` не пользуется, поэтому античит не затрагивается; нужно лишь проверить, что `off` содержит выбранного игрока.

## 2. Где считать
Одна SQL-функция `player_numbers(p_device uuid, p_secret text)` (по образцу `set_player_name`: `device_check`, `security definer`, `stable`), возвращает один JSON со всеми блоками. Клиент только рисует. Считать на клиенте не стоит: потребуется скачать все `xi` (десятки КБ на 100 сезонов, сотни — на 1000) и придётся читать их в обход RPC.
- Нагрузка: выборка по `seasons_player_idx`; 1000 сезонов × 11 элементов `xi` = 11 000 строк после `jsonb_array_elements`, группировки в памяти, оценка — десятки миллисекунд (проверить `explain analyze` на тестовой базе с 1000 синтетических сезонов). Для 100 сезонов — единицы миллисекунд.
- Кэш: клиент хранит ответ в `localStorage` с меткой числа сезонов и перечитывает только если после последнего чтения был новый сезон или прошло более 10 минут; один вызов на открытие раздела, не на каждый рендер. Серверная материализация не нужна, пока игроков с более чем 1000 сезонов единицы; если появится — таблица-кэш `player_numbers_cache` с обновлением при сохранении сезона (только сервером).
- Чужие страницы: раздел только на своей (история сезонов — личное). Публичной остаётся сводка `player_profile_pub`.
- SQL: новый файл `sql/v08x_player_numbers.sql`, только добавление, повторно запускаемый, затем `check_schema.sql`.

## 3. MVP и вторая очередь
MVP (6 блоков, без новых данных и новой таблицы; один выпуск, ориентир до 400 строк без генерируемых файлов):
1. Заголовок-вывод о стиле.
2. «Твій рекорд» (сезоны, % побед, В/Н/П, очки, лучший сезон, голы).
3. «Твоя 11-ка» (поле, тап по футболке — карточка игрока без пункта «взял из предложенных»).
4. Бомбардир и самый частый.
5. «Один сезон і більше ніколи» + андердог.
6. Очки по режимам + откуда игроки (доли по клубам) — одним блоком-диаграммой.

Вторая очередь: «Відхилені» (после накопления данных: сначала только запись `off`, в MVP-выпуск добавить сразу, чтобы данные копились); вехи; «Клуб 100»; сравнение с лигами (процентили, только если в лиге не менее 5 игроков, без имён); карточка-картинка «поделиться».
Запись `off` желательно включить в MVP-выпуск (маленькая правка `save.js` + таблица), чтобы к выпуску «Відхилені» уже было что показывать.

## 4. Заголовок-вывод: шаблоны (проверяются сверху вниз, показываем первый сработавший; нужно не менее 5 сезонов, иначе нейтральная строка «Зіграй ще кілька сезонів, і ми розкажемо, який ти тренер»)
Метрики: `once` — доля разных игроков, взятых один раз; `top` — доля сезонов с самым частым игроком; `cl` — число разных клубов в составах; `avg` — средний `r0`; `dog` — доля игроков с `r0 ≤ 80`; `fm` — доля сезонов в любимой схеме.
1. `once ≥ 50%`: «Ти не збираєш склад, а влаштовуєш перегляд: {once}% гравців ти взяв лише раз.»
2. `top ≥ 40%` (или один игрок в ≥ 40% сезонов): «Ти вірний {name}: він у {top}% твоїх складів.»
3. `fm ≥ 80%`: «Ти не змінюєш схему: {fm}% сезонів — {formation}.»
4. `dog ≥ 35%`: «Ти віриш у невідомих: кожен {k}-й гравець у твоєму складі має рейтинг до 80.»
5. `avg ≥ 86`: «Тобі потрібні лише зірки: середній рейтинг твоїх гравців {avg}.»
6. `cl ≥ 45` (разных клубов за ≥ 20 сезонов): «Ти збираєш склад з усієї ліги: {cl} різних клубів.»
7. один клуб ≥ 25% игроков: «Твоє серце в {club}: {pct}% гравців звідти.»
8. иначе: «Ти грав різно: {n} сезонів, жодного явного звичаю.»
Пороги стартовые, подобрать по распределению на реальных игроках (запрос по тестовой/основной базе перед выпуском). Тексты без номеров версий и служебных пометок (`tools/tests/player_texts.js`).

## 5. Риски
- Мало сезонов: у большинства игроков их единицы; вывод на 3 сезонах будет шумом. Порог 5 сезонов и мягкие формулировки.
- Данные `xi` до разных версий могут не содержать `g`, `a`, `r0` (поля добавлялись позже): считать с `coalesce`, в блоках показывать «з N сезонів».
- Объединённые игроки (`merge_players`) и удаление аккаунта: цифры считаются по `player_id` после слияния; `delete_player` должен стирать `season_offers`.
- Нагрузка у героев-игроков (1000+ сезонов) и холодный старт RPC; кэш на клиенте и `explain analyze` до выпуска.
- Дизайн: по правилу владельца обязательно через impeccable, макет на утверждение до кода.
